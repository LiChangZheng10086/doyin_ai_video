# 发布中心「渠道」分栏设计（抖音图文 / 今日头条文章 / 视频人工交付）

- 日期：2026-09-18
- 触发：用户反馈「发布这一块，不太喜欢，应该区分出抖音发布和今日头条发布」
  （当时一条列表把「抖音图文（自动提交）」与「今日头条文章（自动提交）」混在一起，
  只能靠平台下拉过滤，动作文案挤在同一行）
- 状态：已实现（见 `docs/superpowers/plans/2026-09-18-publishing-channel-tabs.md`）

## 1. 问题

发布中心现在把三类**性质完全不同**的东西放在同一条列表里：

| 东西 | 谁在提交 | 发布前必经 | 提交后 |
| --- | --- | --- | --- |
| 抖音图文包（`note × douyin`） | 外部 `sau` 引擎自动提交 | 包级预览（`previewRevision`） | 人工核实后「标记已发布」 |
| 今日头条文章包（`article × toutiao`） | 自研 Playwright 执行器 | 同上 | 同上 |
| 视频包（`video × 抖音/小红书/视频号/B站`） | **没有人自动提交**，纯人工交付 | 无 | 人工复制文案、打开平台、自行发布 |

后果（用户直接感受）：

- 一个「全部平台」下拉承担了本应属于一级导航的分流职责；
- 状态页签的计数把三类混在一起，看不出「头条这边还剩几篇」；
- 头条文章包所在的行与视频包长得一样，而它们的「下一步」根本不是一回事。

## 2. 决策（已与用户确认）

**一级「渠道」页签，三个渠道，同一页内切换。**

用户从两个问题里选定的形状：

- 形状：**A. 同一页顶部加一级「渠道」页签**（不是左右并列两块，也不是拆成两个导航入口）；
- 渠道清单：**抖音图文 / 今日头条文章 / 视频人工交付**（三分，不设含糊的「其他」）。

理由（为什么不选另外两个）：左右并列会让列表变长且状态筛选要做两遍；拆导航则无处安放
「视频人工交付」这一大类（它横跨 4 个平台，不属于任何单一平台入口）。

## 3. 渠道模型

```ts
export type PublishChannelId = "douyin-note" | "toutiao-article" | "video-manual";

export interface PublishChannel {
  id: PublishChannelId;
  label: string;              // 页签文案
  contentType: PackageContentType;  // note | article | video
  platforms: PublishPlatform[];     // 该渠道允许出现的平台（用于平台筛选下拉与空态文案）
  hint: string;               // 页签下方一句话：谁在提交 / 需要什么前置条件
  emptyHint: string;          // 该渠道为空时怎么做（指向具体入口）
}
```

**关键点：`contentType` 就是渠道的唯一真源。** 现有构造保证三者互斥：

- `note` 只可能配 `douyin`（`PUBLISH_NOTE_POLICIES` 只有抖音）；
- `article` 只可能配 `toutiao`（服务层 `assertArticlePlatforms`）；
- 其余都是 `video`。

因此**服务端只需要一个新过滤字段 `contentType`**，不必引入「渠道」这种复合查询。
（渠道里的 `platforms` 只用于界面：决定平台下拉要不要显示、空态文案指向哪个入口。）

## 4. 服务端改动（最小）

1. `PublishingListFilters` 新增可选 `contentType?: PackageContentType`。
2. `PublishingStore.list()` 按 `packageRecord.contentType ?? "video"` 过滤
   —— 与 `verifyPackageHealth` 等处同一口径（缺省即视频）。
3. `GET /api/publishing/packages?contentType=note|article|video`：非法值 400
   （与其他筛选参数一致：`invalid("发布内容类型筛选无效")`）。

**不做**的事：不新增渠道级接口、不在服务端存「渠道」字段、不动状态语义。
状态筛选（待处理/待发布/资产异常/垃圾桶…）仍由服务端定义，前端只传参 —— 避免出现
「前端复刻一遍待处理语义」这种必然漂移的第二真源。

## 5. 界面改动

### 5.1 渠道页签（新增，位于状态页签之上）

- 三个页签，各自显示**该渠道的数量**；选中态持久化在 URL（`?channel=toutiao-article`），
  刷新/返回/分享链接都还原到同一视图。
- 缺省渠道：`douyin-note`（抖音图文是既有主通路）。
- 页签下方一行 `hint`，说清这个渠道由谁提交、前置条件是什么：
  - 抖音图文：外部 `sau` 引擎自动提交，需配置 `SAU_BINARY`/`SAU_BASE_DIR`；
  - 今日头条文章：自研执行器自动提交，需先在「设置 → 今日头条」扫码登录；
  - 视频人工交付：**不会自动上传**，只准备交付包，由人工复制文案后到平台发布。

### 5.2 计数（修正既有的「局部计数」）

现状：状态页签的计数是**在当前已加载（已被状态筛选过）的列表上**再数一遍，
所以「失败」页签在「待处理」视图里永远显示 0 —— 数字看着像真的，其实是局部量。

改为：每次加载同时取一次 `status=all`（**不加渠道过滤**）的轻量结果，用它算两份计数：

- 渠道页签计数：按 `contentType` 分组计数（不含垃圾桶，与 `all` 口径一致）；
- 状态页签计数：**当前渠道内**按任务状态计数。

列表本身仍走服务端筛选（渠道 + 状态 + 其他筛选），前端不复刻状态语义。

### 5.3 渠道感知的界面元素

- **平台下拉**：渠道只有一个平台时（抖音图文 / 今日头条文章）不显示，避免出现
  「选了头条图文却把列表筛空」这种自相矛盾的操作；视频人工交付保留（4 个平台）。
- **空态**：按渠道给出可照抄的入口，例如
  「还没有抖音图文包 → 作品详情页成果画布 →「创建图文包」」、
  「还没有头条文章包 → …「创建头条文章包」」、
  「还没有视频交付包 → …「加入发布中心」」。
- 任务行的动作文案**已经是**平台感知的（`提交到头条号` / `发布图文到抖音`），本轮不动。

### 5.4 不做的事

- 不改后端状态语义、不改 `previewRevision` 约束、不改动作可用性规则；
- 不为渠道加二级导航（`:id` 详情页仍是同一个）；
- 不在本轮做「渠道级批量操作」（例如「把本渠道待发布的全排期」）—— 单独评估。

## 6. 验收标准

1. 三个渠道页签可切换，URL 同步（可复制链接还原视图）；缺省落在抖音图文。
2. 每个渠道只显示该渠道的包（`contentType` 一致），且渠道页签上的数字等于该渠道的包数。
3. 状态页签的计数是**完整**的（在一个渠道内跨状态为真），不再是「当前视图的局部量」。
4. 抖音图文章节不显示平台下拉；视频人工交付显示（含 4 个平台）。
5. 空渠道给出指向具体入口的文案，而不是一片空白。
6. 后端 `contentType` 过滤非法值返回 400；不传时行为与改动前完全一致（既有用例全绿）。
7. 文档同步：本 spec、计划文件、`AGENTS.md` / `CLAUDE.md`（逐字节一致）、`docs/worklog.md`。

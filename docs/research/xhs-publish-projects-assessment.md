# 小红书图文发布 参考项目调研评估

> 调研对象：用户提供的 11 个「小红书自动发布」参考项目清单 + 清单外自查发现的 6 个同赛道项目（共 17 个，逐个核实存在性）
> 调研方式：GitHub REST API 核实元数据（星数 / 语言 / 最后推送 / 归档 / 许可）+ 4 路并行 `git clone --depth 1` 逐文件读源码 + 官方公告原文核对
> 调研日期：2026-09-20
> 证据分级：**【事实·源码】**= 直接读到的代码行（附 `path:line`）；**【事实·公告】**= 官方公告 / 正规媒体报道原文；**【事实·issue】**= 项目 issue 区可查的用户反馈；**【事实·API】**= GitHub API 返回值；**【推断】**= 基于上述事实的判断

---

## 0. 一句话结论

**可以做，但这是三条发布通路里风险最高的一条，而且能借的只有「选择器情报」，架构一行都不该照抄。**

- **技术上**：走我们**已有的 Playwright + 持久化 profile + 扫码登录**这条路（与今日头条执行器同一范式），零新增运行时依赖，不需要装 Python、不需要 ChromeDriver、不需要外部引擎。逆向 API 路线（`ReaJason/xhs`、`Spider_XHS`、`XHS_ALL_IN_ONE`）对我们是**不可行**的。
- **风险上**：这是本项目第一次遇到**平台明文把「自动化发布」本身写成封禁理由**的情况，而且执法规模是公开的：2026-03-10 公告逐字写明「通过 AI 托管工具…发布」或「主页所有公开笔记均为 AI 托管代发」→ **封禁**；2026-02-12 公告要求 AI 生成内容必须主动标识（**未标识将限制分发**）；2026-07 通报处置 **42 万**账号、拦截 **302 万**脚本账号、约 **13 万**「AI 托管发布」账号被封号或禁言。**「1 篇也封」的案例存在**，频率不是可靠的安全阀。更麻烦的是：**「点完发布后再去页面读回确认」这个动作本身被报为封号诱因**（§4.4）—— 而那正是我们头条执行器最引以为傲的一环。
- **可借的东西**：跨 4 个项目收敛出一份**发布页选择器清单**（标题 / 正文 / 图片 / 发布按钮 / 登录判定），以及 3 个已被验证的坑。这些**必须再跑一次只读侦察校准**，不能直接抄 —— 与头条那轮「借流程思路、不照抄选择器」同一个结论。
- **不能借的东西**：**8 个实现里没有一个**在提交前读回表单值，**没有一个**提供可信的「已提交但未确认」语义。我们头条执行器的 fail-closed + 读回校验 + `submitted ≠ published` 这套纪律，在这条赛道上没有同行者，只能自己写。

**建议**：先做**只读侦察 + 一份 spec**，并且把「发布频率闸门」「AI 标识声明」「发布后不做读回」当成**功能的一部分**而不是可选项。**但读完 §4 之后必须正视一件事：按现有证据，「无人值守的自动发布」不是本赛道可以承诺的产品能力**；风险最低的形态是**自动化止于草稿、最后一下由真人在真机/真浏览器里点**（§6 给出两种姿态的对比）。

## 2. 三条路线，只有一条适合我们

### 路线 A：浏览器自动化（Playwright 驱动真实 `creator.xiaohongshu.com`）✅ 推荐

与现有头条执行器**同一范式**：持久化 profile + 扫码登录 + 每步读回 + fail-closed + `submitted ≠ published`。

**【事实·源码】一个对我们有利的差异**：小红书发布页的 `input[type=file]` 是**常驻**的，4 个项目全部用 `setInputFiles` / `DOM.setFileInputFiles` 直接送文件，**没有一个需要处理原生文件选择框**。这比头条那套「点加号 → 抽屉 → 接 `filechooser` 事件 → 关抽屉」简单得多（头条那两个坑在这里不存在）。

**【事实·源码】但有一个新坑**：页面上的**第一个 `input[type=file]` 是视频上传框**。`SvenKunkka/xhs-auto-deepseek:896-921` 专门处理了这点 —— 必须按 `accept` 含 `image/png|jpg|jpeg|webp` 或带 `multiple` 来挑。裸取 `.first` 会把图片送进视频框。

### 路线 B：逆向私有 API（`ReaJason/xhs` / `Spider_XHS` / `XHS_ALL_IN_ONE`）❌ 不可行

**【事实·源码】三个理由，每个都独立成立：**

1. **签名是 vendored 复刻，且一两周就变一次。** `Spider_XHS` 的 README 更新日志显示算法连番升级（25/07/15 xs v56、26/04/11、26/07/25、26/09/07 X-s 4.4.3 / webBuild 1.26.0）；它的签名 JS 要靠 **node 子进程**执行，`x-rap-param` 依赖一个**冻结的 436B 浏览器抓包指纹**（`xhs_utils/xhs_creator/js/rap_fingerprint_creator.json`），而该指纹**自 2026-07-25 起未再更新**。另有一处运行时依赖线上：从 `as.xiaohongshu.com/api/sec/v1/ds` 拉服务端下发的 DS 程序。
2. **`ReaJason/xhs` 的默认发布路径是坏的。** 仓内虽有一个纯 Python `sign()`（`xhs/help.py:15-58`），但它的最后提交是 **2024-01-13**，且只用于 `quick_sign=True` 的 creator/customer 分支；`create_note` 走的是 `external_sign(url, data, a1=, web_session=)`，而 `help.sign` **没有 `web_session` 形参** → 默认路径直接 `TypeError`。它自己的文档因此要求你**另起一个服务，用真实站点里的 `window._webmsxyw` 算签名** —— 也就是说**纯 API 路线最终还是要一个浏览器**。
3. **已经有失效实测。** `XHS_ALL_IN_ONE` 开放 issue #27（2026-09-03）：「发布接口 `/web_api/sns/v2/note` 返回 HTTP 406 code=-1（疑似 Creator rap 指纹模板过期）」，作者未回复。

**【推断】** 顺带纠正清单里两条说法：「基于 xhs SDK 直连接口不开浏览器，30 秒一篇，成功率 >95%」与「xhs SDK 逆向了签名算法并透明封装」—— 前者与上面第 2 条直接冲突，后者忽略了那个 `sign()` 已经 20 个月没动、且默认路径用不上。`DaBaoAgent/xhs-post` 只有 3 星、且与同作者的另一个仓库同体积，那两条性能数字没有可核实的来源。

**结论**：这条路要引入 Python + Node 双运行时、要跟着平台抓指纹，还违反平台公告；而它能做的「发出图文」，我们用自己的 Playwright 一样能做，且可控性高一个量级。

### 路线 C：MCP / Agent Skill 包装层 ❌ 不适合

**【事实·源码】** 三个被评估的 MCP/Skill 项目，真正有价值的部分都被证明是**包装而非能力**：

- `ShunL12324/xhs-mcp` 的「草稿流」是**它自己数据目录里的 SQLite 表** `note_drafts`（`db/schema.ts:105-114`），CRUD 全程不开浏览器；**仓库里没有任何平台侧草稿端点**。
- 它的「定时发布」是 stub：点了「定时发布」单选框后 `log.warn('Schedule time selection not fully implemented')`，**从不填日期**，却把本地状态记成 `'scheduled'`（`tools/publish.ts:122`）。
- `aki66938/xhs-toolkit` **完全没有草稿、也没有发布定时**（`src/` 里 `draft` 零命中；`data/scheduler.py` 是纯采集的 APScheduler）。

**【推断】** 我们的架构是自托管 Electron + 本地 HTTP，不接 MCP 运行时；而「草稿」这个概念在小红书侧**未经证实存在**，我们已有的服务端 `previewRevision` 必经确认闸门是自建且更强的，不该换成任何第三方的草稿模型。

## 3. 可复用的选择器情报（最高价值的部分）

**【事实·源码】跨项目收敛的选择器**（4 个真正走到发布表单的项目）：

| 环节 | 共识写法 | 出处 |
| --- | --- | --- |
| 发布页 URL | `https://creator.xiaohongshu.com/publish/publish`（可带 `?source=official`） | post-to-xhs:101、xhs-publisher:45、helloxiaohong `config.js:60` |
| 必须先进「图文」页签 | 按**文本**「上传图文」匹配后点击（**不要用 class**） | 3/3 到表单的项目都这么做 |
| 图片上传 | 常驻 `input[type="file"]` + `setInputFiles`；**必须排除第一个视频框** | 4/4；坑见 xhs-auto-deepseek:896-921 |
| 标题 | `input[placeholder*="标题"]`（宽松匹配）→ 兜底 `div.d-input input` | 4/4 |
| 正文 | `div.ProseMirror[contenteditable="true"]` / `div.tiptap.ProseMirror`（**TipTap**） | 3/4；`div.ql-editor` 是 Quill 时代残留 |
| 话题 | 在正文编辑器里打 `#词` → 等联想 → 点首项 / 回车；**失败即退化为纯文本** | 2/2；**没有任何项目给出稳定的联想弹层选择器** |
| 发布按钮 | 按文案「发布」匹配（**必须精确**，侧栏有「发布笔记」、表单有「定时发布」） | 3/4 |
| 成功判据 | `text=发布成功`，或 URL 离开 `/publish/publish` | 2+/4 |
| 登录判定 | **页面信号优先于 cookie**：READY（「上传图文」/ 标题框 / 编辑器）∧ ¬BLOCKER（「扫码登录」/ `img[src*="qrcode"]`） | xhs-auto-deepseek:739-767 |
| 图片预览计数 | `.img-preview-area .pr` 或 `.img-container, .pr, .preview-item` | post-to-xhs:149、xhs-auto-deepseek:927 |

**【事实·源码】已被时间判死、不要抄的**：`填写标题`（post-to-xhs:137）、`填写能获得更多赞哦`（xhs-auto-publisher:261）——与头条那次「填写作品标题 → 添加作品标题」同型，**只有 `*="标题"` 活了下来**。

**【事实·源码】三条已被踩过的坑，可以直接省我们时间：**

1. **复用日常 Chrome profile 不可行**。`xhs-auto-deepseek:105-125` 实测记录：在体积很大的日常 profile 上 `launch_persistent_context` **50 秒不出窗口**（全新 profile 0.9 秒成功）；且 `connect_over_cdp` 被 Chrome 136+ 拒绝（"remote debugging requires a non-default data directory"）。→ 必须用我们自己的专用 profile 目录（与头条 `storage/toutiao/profile` 同做法）。
2. **登录判定不能只看 cookie**。`access-token-creator` / `galaxy_creator_session_id` 这类 cookie **未登录访客也会被种**，只看 cookie 会误判为已登录。→ 用「页面 READY ∧ 无 BLOCKER」，cookie 只作旁证。**这正好呼应我们头条那轮的 `LOGIN_CHECK_ATTEMPTS = 2`。**
3. **发布按钮必须精确匹配文案**。侧栏有「发布笔记」、表单里有「定时发布」，宽松匹配会点错。

### 8 个项目的「诚实性」评级（这一栏比选择器更值得我们看）

**【事实·源码】** 我们的头条执行器是在「参考项目吞掉失败」这件事上吃过教训才长出来的（AGENTS.md 记录了 `mf-yang/toutiao-ops` 封面上传失败也返回「发布成功」）。这条赛道上**同样的问题普遍存在，而且更严重**：

| 项目 | 问题 |
| --- | --- |
| `post-to-xhs` | `_click_publish()` 之后**无条件** `print("PUBLISH_STATUS: PUBLISHED")`（`publish_pipeline.py:652`）；话题选中是**假成功**（内联 JS 只要找到编辑器就 `return ok:true, selected:true`，从不读回）；标题/正文写入无读回 |
| `jogholy/xhs-publisher` | **图片上传失败只 `log.warning` 然后继续填表并点发布**（:272-273）→ 可能发出**零图**笔记；重试最多 3 次，**第 1 次真点出去了、后续断言抛异常就会再点一次** → 重复发帖 |
| `xhs-toolkit` | `success=True` 从**每一个分支**返回，含异常分支（`publisher.py:288-319`） |
| `xhs-mcp` | 成功判据是 `url.includes('publish')` —— **发布页 URL 本身就含 "publish"**，等于什么都没判（`services/publish.ts:241`） |
| `Insomnia501/xhs-auto-publisher` | 结尾 `🎉 完整自动发布流程执行完成！` 在「没找到发布按钮」时**同样打印**（:346） |
| `XHS_Auto_Publish` | 点完发布 + 睡 5 秒后无条件 `return True`（:336-342） |
| ✅ `xhs-publisher`（唯一亮点） | 它是**唯一**给出「发布状态不确定」（`uncertain: True`，且该出口不重试）的项目 |

**【推断】** 结论很直接：**这 8 个项目没有一个可以作为我们执行器的实现参考**，只能作为选择器校准数据。我们已有的四条纪律（读回比内容不比有无 / 任何失败停在点发布之前 / 拿不到判据就如实记 unconfirmed / 绝不自动重试）在这条赛道上没有现成实现可抄。

## 4. ⚠️ 平台侧风险（本节是本文最重要的部分）

### 4.1 【事实·公告】2026-03-10《关于打击 AI 托管运营账号的治理公告》

逐字原文（[光明网转洪观新闻/界面新闻](https://m.gmw.cn/2026-03/10/content_1304371172.htm)）：

> 平台近期发现部分用户采用 AI 托管模式运营账号，通过技术手段自动生成内容、发布笔记，并在评论、私信、群聊等场景中模拟真人互动。平台严格禁止任何利用技术手段模拟真人、进行非真实内容创作或虚假互动的行为。
>
> 即日起，平台将对 AI 托管类账号实行以下治理措施：
> 1、对于普通账号**偶发**使用 AI 托管代写、代发笔记或进行互动，平台将根据违规程度，采取**警告、限制内容分发**等梯度处理措施。
> 2、对于**直接通过 AI 托管工具注册、发布、互动的账号**，或**主页所有公开笔记均为 AI 托管代发的账号**，平台将予以**封禁**处理。

**【推断】这条公告对我们的设计有两条**硬约束**（不是建议）：

- **封禁条款 2 的第二个条件正好描述「全自动矩阵号」的终局形态**：如果用户把这个应用当成唯一发布入口，一段时间后主页上所有公开笔记就都是机器发的 → 正落在封禁口径里。所以功能设计上**必须让账号里存在相当比例的人工发布内容**，并把发布频率压到「偶发」档。
- **第一个条件点名「注册」和「互动」**：我们**绝不能**扩展到自动注册、自动评论/私信/点赞收藏。这正好也把那几个「全链路」（采集 + 互动 + 发布）项目排除在参考范围外。

### 4.2 【事实·公告】2026-02-12《关于加强自主标识 AI 生成合成标识的公告》

逐字要点（[澎湃新闻](https://www.thepaper.cn/newsDetail_forward_32599956)）：

> 小红书呼吁用户在发布由 AI 生成合成的图文或视频内容时，主动添加 AI 生成合成标识……如创作者在发布环节未主动对 AI 生成合成内容做标记，平台将基于检测结果对未声明内容添加标识。**此类未主动标识的 AI 生成合成内容，平台将限制分发。**

同日「网信中国」通报：依法依约处置账号 **13421 个**，其中点名「分享去除 AI 标识教程」的小红书账号亦被处置。

**【推断】** 我们的内容**整条都是 AI 的**（AI 洗稿 + HyperFrames 渲染的静帧），所以「AI 合成内容标识」对我们是**必填项，不是可选项**。`jogholy/xhs-publisher` 已经因此增加了这个声明步骤（`SKILL.md:326` 记录该要求自 2026-02-12 起严格执行，代码在 :419-441 找「添加内容类型声明」→「AI合成内容」）。**这个声明环节必须进 spec，并且必须读回校验**（漏掉 = 内容被限流，用户还以为是发成功了）。

**【事实·issue】对抗手段被证伪**：`#680` 有用户称「从 playwright, patchright, camoufox, bitbrowser N 个方案，**没有一个能解决不被识别的问题**」。

**【事实·issue】同一项目的自我矛盾**：`xiaohongshu-mcp` 的 README 自称「原项目运行一年多没封过号」「建议每天 50 篇」，而其 PR #773（2026-07-27）承认「issue 区有较多封号与警告的反馈」——**README 的乐观说法不可用**。

**【推断】** 四点判断（**较本文档初稿已按新证据修正**）：

1. **「发布」是政策点名的目标，不只是「互动」的附带风险。** 4.1 的封禁条款第二个条件直接描述「通过 AI 托管工具发布」，而 2026-07 的通报把「自动生成 + 自动发布」单列为处置对象。**「只发文、不互动」不等于安全。**
2. **频率不是可靠的安全阀。** 1 篇就永久封号的案例存在；6 篇/天也有；「仅自己可见」也不能豁免（#680）。
3. **风控与 IP/环境强相关，云服务器是明确高危。** #777 家庭网络仍被警告；维护者 2026-08-02 明确建议住宅 IP，并称 IP 本身是检测因素。→ 若将来做，**只能在本机跑**（桌面端天然符合）。
4. **账号价值决定风险承受度**。前述量级说明这不是边缘现象；**产品文案必须写明「风险由账号承担、平台可封号」，不能承诺安全**。

### 4.4 ⚠️ 对本文档作者先前判断的一处更正：**「发布后读回确认」本身有风险**

**这是本轮最反直觉、也最影响设计的一条。**

**【事实·issue】** `xiaohongshu-mcp` #715（2026-06-15）：

> 「我用发布是没问题的，有两次让 ai **确认一下发布成功了没有**，结果第一次警告第二次七天」

**【推断】** 这条直接冲击我们**引以为傲的那条设计**：头条执行器的 `submitAndConfirm` 会在点完发布后**继续在页面上读回结果**、抓 `postConfirm` 证据（URL / 是否离开页面 / 可见文案头尾）。在小红书上，**这个「点完之后还去页面里翻看」的行为本身就是被封的原因之一**——与「只读操作也被封」（§4.3 的 #726/#728/#777）是同一个机制：平台检测的是**自动化访问模式**，不是单次动作的性质。

因此若要做这条通路，**发布后的读回策略必须改**：

- **不要在点完发布后继续抓页面证据**（不抓 postConfirm、不做成功文案轮询）；点完即断开，结果如实记为 `unconfirmed`，由人工在自己的 App / 真浏览器里核实。
- 这与我们既有的「机器只记已提交、是否真发出由人工核实」不变式**方向一致**，但要更进一步：**连核实动作也不要由自动化去做**。
- 代价要说清楚：**我们会比头条那条通路拿到更少的证据**，`verification: "unconfirmed"` 会成为**常态而非例外**。

### 4.5 官方 API 路线（结论：已核实，个人用户没有）

**【事实·API】** 已核实开放平台自己的接口目录 `https://open.xiaohongshu.com/api/doc/list`，只返回 **公共 / 订单 / 售后 / 商品 / 库存 / 素材中心 / 物流 / 财务** 八类，**全部是电商能力，没有任何笔记发布/草稿接口**。

**【推断】** 普通账号唯一「官方」路径就是**真人在创作服务平台或 App 里手动发布**（并由真人决定 AI 内容的标识）。所以不存在「换个更合规的接口来做自动化」这条退路 —— 要么自动化（承担封号风险），要么人工。

**【事实·源码】三个必须提前决策的连带问题：**

1. **渠道分栏会破功。** `PUBLISH_CHANNELS` 的「抖音图文」渠道是 `contentType: 'note'` + `platforms: ['douyin']`，而 `publishChannelOf()` / `selectChannelPackages()` **只按 `contentType` 归属**。小红书图文一进来，`note` 渠道就变成**双平台**：
   - 选项甲：渠道合并成「图文（抖音 / 小红书）」，`platforms: ['douyin','xiaohongshu']` → 按既有约定（多平台渠道才显示平台下拉）自动长出平台筛选，**改动最小**；
   - 选项乙：拆成两个渠道 → 需要把渠道身份从 `contentType` 改成 `(contentType, platform)`，**直接推翻 AGENTS.md 里「渠道 = 内容类型的界面投影」这条不变式**，影响 `publishChannelOf` / `selectChannelPackages` / 计数与 URL query 那一整套。
   → **建议甲**。但这条必须由你拍板，因为它改的是你已经验收过的界面约定。
2. **图片比例：我们现在只有 9:16，小红书首图要 3:4。** 场景静帧是 **1080×1920（9:16）**；小红书笔记配图官方推荐 **3:4（1080×1440）**，且**同一篇笔记只能有一种比例**（[标记侠规格汇总 2026](https://www.biaojixia.com/specs/xiaohongshu?scenario=spec-xiaohongshu)，另两个独立项目也都固定输出 1080×1440 / 1242×1656）。直接上传 9:16 会被裁切/留白。→ 需要一层 **3:4 裁切**，实现范式可直接复用 `toutiao-media.ts` 的 `prepareCoverImage`（`scale=…:force_original_aspect_ratio=increase,crop=…` + 产物大小校验 + 失败即删不留半成品），按项目惯例**新建 `note-media.ts`（原拟名 `xhs-media.ts`；因最终选定"打包时裁"，它成了**平台中立**的模块，故改名） 自带错误码**，不去改头条/公众号那两个已测模块。
   - 注意：抖音图文包当初**明确写了「不做图片裁剪」**（`2026-09-17-douyin-note-auto-publish-design.md` §10），这次是**首次把裁剪纳入范围**。
3. **AI 标识声明要进包模型与指纹。** 与头条的 `toutiaoOptions`（首发/声明/微头条）**参与 `previewRevision`** 同一口径：小红书的「AI 合成内容标识」若参与提交，就必须进包级指纹，否则「预览时没勾、提交时勾了」不会被拦下。

## 6. 建议的落地路线

### 6.1 两种姿态，必须先选一个

**【推断】** §4 的证据出来之后，「做到哪一步」变成了一个**产品决策**而不是技术决策：

| | 姿态甲：自动提交（现状设计） | 姿态乙：**自动到草稿为止**（推荐） |
| --- | --- | --- |
| 程序做什么 | 填表 → 勾声明 → 点「发布」 | 生成文案 + 3:4 图片 + 填表 → **停手** |
| 谁点最后一下 | 程序 | **真人**（在自己的 App / 真浏览器里） |
| 与公告的关系 | 正落在「通过 AI 托管工具…发布」+「主页所有公开笔记均为 AI 托管代发」两条封禁口径上 | 与公告口径**不直接冲突**（发布主体是人） |
| 已有证据 | 1 篇即永封、2 天即封、6 篇/天即封；机械节奏即封 | **无实测证据**（这是它的主要不确定性） |
| 我们能保住的不变式 | 需要放弃「发布后读回」（§4.4） | 读回问题不存在（我们本来就不点发布） |
| 工作量 | 全套执行器 + 提交闸门 | 几乎一样（差别只在最后一步点不点） |

**【推断】** 两条路**共享 90% 的实现**（浏览器、登录、选择器、读回填表、3:4 裁图、AI 声明勾选）。所以正确的做法不是「现在就在两者之间赌一把」，而是**先把共享的那 90% 建起来，把「是否真的点发布」做成最后一步的开关** —— 侦察与 spec 对两种姿态都成立。

### 6.2 分步

**【推断】** 分四步，前两步零风险且必需：

1. **只读侦察（需要你扫码一次）**：写一个 `scripts/probe-xhs-publish-page.ts`，进登录页 → 进 `creator.xiaohongshu.com/publish/publish` → 落 DOM 快照与选择器清单，**不填表、不上传、不点发布**。目标是把 §3 的选择器在我们的账号上校准一遍，并回答几个只有真页面能回答的问题：
   - 「上传图文」页签在未登录/已登录两态下的 DOM 差异；
   - 是否真有「AI 合成内容标识 / 内容类型声明」控件，文案是什么（**决定合规能否满足**）；
   - 笔记配图对 9:16 的实际处理（是否强裁），以确认 3:4 方案；
   - 话题联想的稳定容器选择器（**§3 里唯一没有共识的一项**）。
2. **写 spec**（`docs/superpowers/specs/…-xiaohongshu-note-publish-design.md`），把 §4 的风险、§5 的三个决策、以及下面这些**固化成不变量**：
   - 发布频率闸门（**每日 ≤1 篇**）+ 同一账号并发互斥（沿用既有 409 语义与 30 分钟僵死阈值）。**但要在 spec 里写明它只是降低概率、不是安全保证**（§4.3 有「1 篇即永封」的案例）；
   - **AI 合成内容标识必须真的勾上并读回**，勾不上就 fail closed（照头条 `ensureWeitoutiaoUnchecked` 的「已是目标状态就不点 → 不是就点 → 读回 → 改不掉才 fail closed」范式）；
   - ⚠️ **点完发布后不再读回页面**（§4.4）：不抓 `postConfirm`、不轮询成功文案，点完即断开，如实记 `unconfirmed`，由**人工在真机/真浏览器**里核实。这条是对头条范式的**刻意偏离**，必须在 spec 里写明理由，否则后人会以为是漏做；
   - `task.status` 全程不变、`verification: confirmed | unconfirmed`、绝不自动重试 —— 三条与抖音/头条**逐字相同**；
   - **不做**自动注册、自动评论/私信/点赞收藏、**也不做任何小红书侧的读取/采集**（§4.3 的 #726/#728/#777/#150 说明只读同等危险）；
   - **不做定时/cron 自动跑**（#680 的 8 小时 cron 被点名）：每次发布都必须是一次显式的人为操作。
3. **实现**：`xhs-browser.ts`（浏览器解析链，复用打包的 chrome-headless-shell）+ `xhs-page.ts`（页面步骤，每步读回）+ `xhs-runner.ts`（扫码登录会话 + 发布编排 + `postConfirm` 证据）+ `note-media.ts`（3:4 裁切，平台中立），全部照头条那四件的结构与测试范式（fixture 用真浏览器跑）。
4. **真机演练**：照头条 `--dry-run` 的先例，先做「填完不发布」的演练（唯一副作用是平台自动存草稿），再让**你本人**在确认后手动跑一次真实发布。

**先要你拍板的三件事**（详见 §5）：渠道怎么并（建议甲）、3:4 裁图怎么定（建议裁）、以及**是否接受 §4 的账号风险**。

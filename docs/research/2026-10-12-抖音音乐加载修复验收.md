# 抖音音乐加载修复验收

## 证据与原因

用户 17:05 的失败记录显示音乐侧栏仍为「加载中」，并无候选歌曲；旧代码只等待匹配卡片 8 秒，就误报歌曲不存在并要求修改歌名。用户网页版截图和本机只读侦察均确认 `Whatever Happens` 可搜索，包含 Michael Jackson 的 1 分钟版本。不能将问题归因于歌名或平台没有该曲。

真实空白图文编辑页无需上传即可打开音乐侧栏。分别实测打开后立即搜索、先等初始列表再搜索，搜索结果在约 2.1 秒、1.6 秒出现。实际请求为 GET `/openapi/aweme/v1/music/search/`，输入在 `keyword`，返回 HTTP 200、`status_code=0` 和 16 个候选。这证明接口和选择器当前可用，未重现用户那一次网络慢加载的底层原因。

## 修复

- 在填入歌名之前监听本轮搜索请求，等待对应响应、响应体和加载结束后才选曲，不使用旧列表。
- 每轮搜索最多等待 30 秒。网络失败或加载超时仅关闭并重新打开音乐侧栏，重新搜索同一歌名一次。真实网页实测表明快速清空再填同名不会重新请求，重开侧栏才能重置其搜索缓存；不重传图片、不重试发布。
- HTTP 错误、业务响应异常、加载未完成、加载完成但无匹配分别提示。持续加载不再要求改歌名。
- 保留歌名精确匹配（忽略大小写和空格）、失败阻止发布、无配乐通路及外部 sau 文件不修改。

## 验收

- 基线隔离复现：9.5 秒加载被旧版 8 秒超时拒绝；永久加载误报改歌名；加载期间点击旧同名卡片。新逻辑对应回归通过。
- 使用实际 Python 适配脚本、patchright 与隔离 Chromium，模拟真实搜索 fetch/响应，覆盖上述加载状态和既有选曲场景。所有测试请求被拦截，不调用真实发布。
- 真实网页首次搜索请求被刻意中断（connectionreset）后，重开音乐侧栏产生第二次请求，并成功应用 `Whatever Happens · 01:00`。使用实际 sau 同一 Python/patchright、Cookie 和 stealth 初始化，未上传或发布。
- 最终正常真实复测输入 `whateverhappens`，同一 sau Cookie、Python/patchright 与 stealth 初始化下，新脚本成功应用 `Whatever Happens`，读回音乐名称和 01:00；未上传图片、填写正文、保存草稿或点击发布。
- 隔离浏览器新增慢加载、永久加载、旧同名列表、HTTP 403、连接中断后重开搜索用例；本次推送前在独立工作树完整运行 16 项全部通过，另 3 项旧版失败复现通过。旧快速清空重填方式也已通过真实网页及缓存模型复现失败，新重开方式请求两次、应用一次。
- `sau-runner` 20 项回归通过，包含 HTTP 503、业务响应异常和失败不能继续提交；后端/前端类型检查和凭据扫描通过。全量 `npm test` 为 1371 通过、1 失败、1 跳过：图集 HTTP 测试出现本地 `UND_ERR_SOCKET`；该文件单独复跑 2 项全部通过，不能把首次全量报告为全绿。

- 最终后端编译产物与实测脚本文本一致；项目已重启，新内嵌后端 59981 健康检查正常。既有文章暂存补丁逐字节保持原样。代码交付、提交链接及剩余验收由 GitHub Issue #23 跟踪。推送前独立工作树再次运行 20 项执行器回归、类型检查、凭据扫描和后端编译通过。

## 边界

本次真实验收覆盖搜索和应用音乐，完整图集最终发布与播放效果仍未验收。按名称选择仍无法区分同名歌曲的歌手或版本。用户原失败的具体网络、服务端或加载竞态原因尚未证实；新增等待与错误区分针对已证实的 8 秒误判处理。未改写真实图集、发布包、平台作品或 Cookie 文件。
